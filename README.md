# Kvant — Product Analytics: адаптивное обучение

**EdTech-кейс по продуктовой аналитике: от поведения ученика до решения о следующей рекомендации.**

Это аналитический кейс на основе моей учебной платформы Kvant. Я специально смотрела на неё уже не как разработчик, а как аналитик: **что можно понять из данных, какое решение можно принять и где данных пока недостаточно.**

## 1. Product question

> **Как определить, какую тему стоит рекомендовать ученику следующей?**

Для этого я использовала четыре группы сигналов:
- performance — accuracy по теме;
- volume — количество попыток;
- activity — дневная активность;
- context — предмет, сложность и прогресс.

Главный принцип анализа: **низкая метрика без достаточного объёма наблюдений ещё не является основанием менять продукт.**

## 2. Что показал анализ

| Сегмент | Попытки | Accuracy | Интерпретация |
|---|---:|---:|---|
| Математика | 117 | 59,0% | большой объём, нужен drill-down по темам |
| История | 36 | 25,0% | заметный сигнал для дальнейшего анализа |
| Английский | 7 | 57,1% | мало наблюдений |
| Древний мир | 23 | **17,4%** | сильный кандидат на дополнительную практику |
| Сложность 1 | 125 | 50,4% | основной объём наблюдений |
| Сложность 2 | 29 | 58,6% | умеренный результат |
| Сложность 3 | 6 | 33,3% | недостаточно данных для решения |

Всего в текущем аналитическом срезе — **160 попыток за 7 активных дат**.

### Почему «Древний мир» становится recommendation candidate

У темы:
- 23 попытки;
- 17,4% accuracy;
- результат значительно ниже 40%-го порога текущей аналитической гипотезы.

Поэтому она попадает в high_review_priority.

Это **не означает**, что я доказала наличие проблемы обучения. Это означает:

> **данных достаточно, чтобы проверить гипотезу дополнительной практикой.**

А вот сложность 3 я не стала бы продвигать в рекомендации: 33,3% выглядит плохо, но это всего 6 наблюдений.

## 3. Decision layer

Чтобы анализ не заканчивался на графике, я перевела его в простое объяснимое правило:

| Условие | Решение |
|---|---|
| < 5 попыток | insufficient_data |
| ≥ 10 попыток и accuracy < 40% | high_review_priority |
| ≥ 5 попыток и accuracy < 60% | review |
| остальные | do_not_prioritize |

Пороги — **аналитическая гипотеза**, а не production-модель. В реальном продукте я бы валидировала их на большем объёме данных и через эксперимент.

### Пример продуктового решения

**Вход:** тема «Древний мир»

**Данные:** 23 попытки → 4 правильных → 17,4% accuracy

**Решение:** high_review_priority

**Действие продукта:** дать дополнительную практику по теме, а не просто перейти к следующей теме.

**Что проверить после рекомендации:** выполняет ли ученик задание и растёт ли его accuracy на последующих попытках.

Именно этот переход — **metric → decision → measurable outcome** — для меня является основной частью кейса.

## 4. SQL

В sql/analytics.sql я собрала несколько типовых аналитических задач:

- пересчёт accuracy из correct / attempts;
- доля попыток предмета через window function;
- weak-topic analysis с minimum-volume guardrail;
- RANK() слабых тем внутри предмета;
- сравнение accuracy темы с accuracy предмета;
- CASE WHEN для recommendation buckets;
- LAG() для изменения активности день к дню;
- cumulative XP через оконную SUM();
- отдельный decision layer с объяснением причины рекомендации.

То есть SQL здесь используется не только для получения таблицы, а для **подготовки данных к продуктовому решению**.

## 5. Python

Python используется как воспроизводимый аналитический слой:

- загрузка CSV;
- пересчёт метрик;
- проверка observation volume;
- формирование recommendation candidates;
- анализ daily activity;
- weighted accuracy;
- визуализация performance по предметам.

Основной файл: kvant_product_analytics.py.

Отдельные агрегаты по сложности вынесены в data/difficulty_performance.csv, поэтому значения не захардкожены внутри скрипта.

## 6. Что я бы проверила следующим шагом

На текущих данных нельзя утверждать, что адаптивная рекомендация улучшает обучение. Поэтому следующий этап — эксперимент.

**Control:** текущая логика рекомендаций.

**Treatment:** рекомендация с учётом performance, recency и progress.

### Primary metrics

- task completion;
- accuracy после рекомендации;
- повторная практика слабых тем;
- D7 retention.

### Guardrails

- skips;
- повтор уже освоенных тем;
- общая активность.

Главный вопрос:

> **Помогает ли персонализация реально лучше учиться, а не просто чаще показывать ученику задания, в которых он ошибается?**

## 7. Ограничения

Это небольшой аналитический срез исходного учебного проекта:

- 160 попыток;
- 7 активных дат;
- один пользователь в текущем аналитическом срезе;
- нет контрольной группы;
- нет полноценной долгосрочной когорты;
- response-time в исходных данных непригоден для анализа.

Поэтому я **не делаю causal claims** и не выдаю текущие результаты за доказательство эффективности адаптивного алгоритма.

## 8. Откуда взялся проект

Kvant — образовательная платформа, которую я разрабатывала в рамках дипломного проекта.

В исходном приложении были адаптивный подбор заданий, диагностическое тестирование, уровни сложности, прогресс по темам, XP и серии активности, предметы и темы, роли ученика и родителя, Django REST API, React-интерфейс и автоматическая генерация заданий.

В этом репозитории я сознательно оставила фокус на аналитической части:

**данные → метрики → проверка качества сигнала → решение → гипотеза → эксперимент.**

## Что этот проект показывает

Для меня этот кейс прежде всего про продуктовый подход:

**не просто найти низкую метрику, а понять, можно ли ей доверять;  
не выдать гипотезу за факт;  
и связать аналитический вывод с конкретным решением, которое можно проверить.**
